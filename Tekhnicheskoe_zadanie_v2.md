# Техническое задание
## Интернет-магазин автозапчастей «Mobis-VLG» (редакция 2.0)

| Параметр | Значение |
|----------|----------|
| Название | Mobis-VLG |
| Платформа | Django 5.x (Python 3.12+) |
| БД (v1) | SQLite (файл), архитектура без привязки к диалекту — миграция на PostgreSQL в v2 |
| Клиент | Django Templates + Bootstrap 5 (или аналог) |
| Админка | Django Admin (кастомизация под операции) |
| API | Не требуется в v1 |
| Хостинг | Beget; статика — WhiteNoise (или аналог); media — защищённая директория |
| Объём каталога | ~150 сейчас, рост до ~1500 позиций |

---

## 1. Цель и границы

### 1.1. Цель
Веб-приложение, в котором:
- клиенты с личным кабинетом заказывают автозапчасти;
- администратор оперативно видит заказы в админке, ведёт приход/расход и заявки на закупку;
- ведётся учёт остатков с резервированием под заказы.

### 1.2. Роли в v1
| Роль | Кто | Права |
|------|-----|--------|
| Администратор | Владелец (один пользователь) | Полный доступ ко всему |
| Клиент | Зарегистрированный пользователь | Каталог, корзина, заказы, история своих заказов |

Роль «Менеджер» в v1 **не реализуется** (заложена в модели User на будущее).

### 1.3. Входит в v1 (MVP)
- Регистрация/вход в ЛК (email + пароль, без подтверждения email).
- Каталог: категории, карточки, фото, поиск по артикулу/названиям/кроссам, фильтры по категории, состоянию, марке/модели авто.
- Корзина и оформление заказа **только из ЛК**.
- Способ получения: самовывоз / доставка (без онлайн-оплаты; расчёт — переводом вне системы).
- Статусы заказа, резерв → списание, отмена с корректным возвратом остатка (до статуса «Отправлен»).
- Склад: приход (в т.ч. частичный из заявки), расход при подтверждении заказа.
- Заявка на закупку со статусами: Создана → В работе → Получено.
- Отчёты + экспорт XLSX.
- Работа администратора через Django Admin.

### 1.4. Не входит в v1 (явно отложено)
| Функция | Когда |
|---------|--------|
| Уведомления в Telegram о новых заказах | v2 |
| Расширенная логистика (Мобис → ТК → В пути → РФ) | v2 |
| Роль менеджера с урезанными правами | v2 |
| Онлайн-оплата / эквайринг | вне scope |
| Возвраты и отмена после «Отправлен» | вручную вне системы |
| Гостевой заказ без ЛК | не планируется |
| Публичный REST API | v2+ по необходимости |
| PostgreSQL | v2 (код сразу совместим) |

### 1.5. Принципы проектирования
1. Складской учёт через **журнал движений**; остаток — проекция (материализованная для скорости).
2. Бизнес-логика в **сервисном слое** (не в views/admin), чтобы позже подключить TG-бота и PostgreSQL без переписывания правил.
3. Модели и ORM без специфики SQLite, кроме настроек подключения.
4. Инварианты остатков проверяются при каждом изменении (см. п. 5.4).

## 2. Клиентская часть (витрина и ЛК)

### 2.1. Авторизация
- Регистрация: email + пароль (email используется как логин). Подтверждение email **не требуется**.
- Вход, выход; восстановление пароля по email — по возможности (если SMTP настроен), иначе смена пароля через админа.
- Социальные сети не используются.

### 2.2. Каталог
На витрине клиенту отображается:
- наименование (рус);
- артикул (SKU);
- цена **только в рублях**;
- состояние (Новый / Б/У);
- наличие (доступный остаток > 0 или «под заказ» — см. п. 2.6);
- изображения;
- краткое/полное описание (рус);
- применимость (марки/модели);
- кросс-номера (для информации и поиска).

Цены в вонах и закупочные цены клиенту **не показываются**.

### 2.3. Поиск и фильтры
**Поиск** (одна строка) по:
- артикулу (SKU);
- наименованию (рус, англ);
- кросс-номерам.

При поиске игнорируются дефисы, пробелы и регистр  
(пример: `ABC123` находит `ABC-123` и `ABC 123`).  
Для этого хранится нормализованный ключ (`sku_normalized` / `cross_normalized`).

**Фильтры:**
- категория (с учётом подкатегорий);
- состояние (новый / Б/У);
- марка автомобиля;
- модель (зависит от марки);
- только в наличии (доступный остаток > 0) — опциональный чекбокс.

**Сортировка:** цена ↑↓, дата добавления.  
**Пагинация:** 20 товаров на страницу (конфиг).

### 2.4. Карточка товара
- Галерея изображений.
- Все поля из п. 2.2.
- Кнопка «В корзину» (доступна только авторизованным; гостю — редирект на вход).

### 2.5. Корзина
- Только для авторизованных.
- Сессия привязана к пользователю (после логина).
- Нельзя добавить количество больше **доступного** остатка.
- При изменении остатка другим заказом — пересчёт/ошибка при оформлении.

### 2.6. Оформление заказа
Обязательные поля:
| Поле | Правило |
|------|---------|
| Имя | обязательно |
| Телефон | обязательно |
| Мессенджер | Telegram / WhatsApp / Max / Imo / Прочее |
| Контакт в мессенджере | ник/номер, обязательно |
| Способ получения | Самовывоз / Доставка |
| Адрес доставки | обязателен, если выбрана «Доставка» |
| Комментарий | опционально |

Оплата онлайн не предусмотрена: в интерфейсе кратко указано, что менеджер свяжется и согласует перевод.

После оформления:
- статус «Новый»;
- позиции **резервируются** (доступный остаток уменьшается, физический — нет);
- клиент видит заказ в истории.

### 2.7. История заказов
Список своих заказов + детальная страница (состав, статусы, способ получения, контакты).

### 2.8. Юридические страницы (минимум)
- Публичная оферта (текст-заглушка, редактируемый).
- Политика обработки ПДн (заглушка).
- Согласие с политикой при регистрации (чекбокс).

## 3. Номенклатура

### 3.1. Языки и валюты
- Наименование: русский + английский.
- Цена продажи: ₽ и ₩ — обе вводятся вручную.
- На витрине — только ₽.
- В админке видны обе цены продажи и закупочные данные по документам.

### 3.2. Поля товара (Product)
| Поле | Описание |
|------|----------|
| Артикул (SKU) | обязательный, уникальный |
| sku_normalized | для поиска, автозаполнение |
| Наименование (рус / англ) | |
| Категория | иерархический справочник |
| Состояние | Новый / Б/У |
| Цена продажи, руб | |
| Цена продажи, вона | только админ |
| Описание (рус) | |
| Активен | boolean; неактивные скрыты с витрины |
| Дата создания | auto |

Единица измерения — фиксированно «шт».

### 3.3. Изображения
- Несколько на товар, порядок сортировки.
- Ограничения v1: JPEG/PNG/WebP; макс. размер файла — 5 МБ; макс. 10 фото на товар (конфиг).

### 3.4. Кросс-номера (ProductCrossNumber)
| Поле | Описание |
|------|----------|
| Товар | FK |
| Номер | текст |
| number_normalized | для поиска |
| Комментарий | опционально (бренд/источник) |

Один товар — много кроссов. Уникальность пары (товар + нормализованный номер).

### 3.5. Применимость к авто
Справочники:
- **CarMake** (марка): наименование, slug.
- **CarModel** (модель): марка FK, наименование, slug; опционально год с–по на уровне связи с товаром.

Связь **ProductVehicle**:
- товар + марка + модель;
- год_с, год_по — опционально.

На витрине и в фильтрах используется эта связь.

### 3.6. Категории
- Наименование (рус), slug, родитель, сортировка.
- Дерево произвольной глубины (на практике 2–3 уровня).

## 4. Заказы

### 4.1. Статусы и переходы
```
Новый → Подтвержден → Собран → Отправлен
  ↓         ↓           ↓
Отменен  Отменен    Отменен
```
Из «Отправлен» отмена **в системе не делается** (возвраты — вне системы, v1).

| Статус | Смысл | Склад |
|--------|--------|--------|
| Новый | Создан клиентом/админом | Резерв |
| Подтвержден | Админ подтвердил | Резерв → расход (списание) |
| Собран | Физически собран | без движения |
| Отправлен | Выдан / передан в доставку | без движения (конечный) |
| Отменен | Отменён | см. ниже |

### 4.2. Отмена
- Из «Новый»: снять резерв.
- Из «Подтвержден» или «Собран»: сторно расхода (вернуть на склад).
- Из «Отправлен»: запрещено в UI.

Резерв **без автоснятия по таймеру** — только решением администратора (отмена или подтверждение).

### 4.3. История статусов заказа
Модель `OrderStatusHistory`: заказ, предыдущий статус, новый, дата/время, пользователь.  
Отображается в админке и (кратко) клиенту в деталях заказа.

### 4.4. Создание заказа администратором
В админке можно создать заказ вручную:
- выбрать клиента (User);
- добавить товары и количества (проверка доступного остатка);
- заполнить контакты и способ получения;
- при необходимости сразу поставить «Подтвержден» (с корректным списанием).

### 4.5. Поля заказа (Order)
- Номер (человекочитаемый, уникальный; формат например `З-ГГГГ-NNNN`).
- Клиент (FK User).
- Имя, телефон, мессенджер, контакт мессенджера.
- Способ получения: pickup / delivery.
- Адрес доставки (nullable).
- Комментарий.
- Статус, даты создания и смены статуса.
- Строки: товар, количество, цена продажи ₽ на момент заказа.

### 4.6. Уведомления
В v1 **не реализуются**.  
В архитектуре: точка расширения `notify_order_created(order)` (заглушка) → в v2 Telegram.

### 4.7. Оперативность для админа (v1)
- В админке список заказов с фильтром по статусу, сортировка «новые сверху».
- Бейдж/счётчик «Новые» на главной админки или в changelist (без push).

## 5. Складской учёт

### 5.1. Модель остатка (Stock)
На товар (OneToOne):
- `quantity_on_hand` — физически на складе;
- `quantity_reserved` — в резерве под заказы в статусе «Новый»;
- `quantity_available` = on_hand − reserved (свойство или денормализация с проверкой).

### 5.2. Журнал движений (StockMovement) — рекомендуется
Каждое изменение остатка — запись:
| Тип | Когда |
|-----|--------|
| IN | Проведение прихода |
| OUT | Подтверждение заказа |
| RESERVE | Оформление заказа «Новый» |
| UNRESERVE | Отмена из «Новый» |
| STORNO_OUT | Отмена из «Подтвержден»/«Собран» |

Поля: товар, тип, количество, дата, пользователь, связь с документом-основанием (GenericFK или явные nullable FK на Order / StockIn).

### 5.3. Приход (StockIn)
Документ поступления:
- дата/время (по умолчанию now, редактируемая);
- поставщик (FK, обязателен);
- признак **проведён** (draft / posted);
- опциональная связь с заявкой на закупку;
- табличная часть: товар, количество, цена закупки ₽ за единицу.

Правила:
- Черновик не меняет остатки.
- Проведение увеличивает `quantity_on_hand` и пишет IN.
- Распроведение в v1 **запрещено** (или только суперпользователем с предупреждением — зафиксировать «запрещено»).
- Ручной приход — для местных закупок и корректировок.
- Приход из заявки — основной путь для импорта (см. п. 6).

### 5.4. Инварианты (обязательны)
1. `quantity_on_hand ≥ 0`, `quantity_reserved ≥ 0`.
2. `quantity_reserved ≤ quantity_on_hand`.
3. `quantity_available ≥ 0` всегда.
4. Нельзя оформить/подтвердить заказ, если не хватает доступного остатка (с учётом резерва этого же заказа).
5. Операции склада — в `transaction.atomic()` с блокировкой строки Stock (`select_for_update`; на SQLite — максимально возможная сериализация).

### 5.5. Расход
Отдельного «ручного расхода» (брак и т.п.) в v1 **нет**.  
Расход только при переходе заказа в «Подтвержден».

### 5.6. Поставщики (Supplier)
Наименование, контактное лицо, телефон, email, адрес (опционально).

## 6. Заявка на закупку

### 6.1. Назначение
Планирование закупки и контроль поступления.  
Остатки меняются **не статусом заявки как таковым**, а создаваемыми/проводимыми документами прихода (в т.ч. частичными).

### 6.2. Формирование
1. По расходу (подтверждённые заказы) за период «с — по» — автоподстановка товаров и количеств.
2. Ручное добавление/правка строк.
3. Комбинация обоих способов.

### 6.3. Номер
Формат: `ЗК-ГГГГ-NNNN` (сквозная в пределах года).

### 6.4. Статусы v1 (упрощённые)
```
Создана → В работе → Получено
```
- Допускается пропуск промежуточных (например, Создана → Получено).
- «Получено» означает, что заявка закрыта как процесс; **не требует**, чтобы все строки были оприходованы на 100%.

Расширенная цепочка (Мобис / ТК / В пути) — **v2**, статусы заложить расширяемым choices.

### 6.5. Табличная часть
| Поле | Описание |
|------|----------|
| № п/п | авто |
| Товар (артикул) | FK |
| Количество к заказу | целое |
| Наименование (англ) | read-only из номенклатуры |
| Цена закупки ₩ / ед. | редактируемая в строке |
| Цена закупки ₽ / ед. | редактируемая в строке |
| Сумма ₩ / ₽ | количество × цена |
| Кол-во оприходовано | сумма по связанным проведённым приходам (вычисляемое) |
| Осталось оприходовать | количество − оприходовано |

### 6.6. Частичный приход (обязательно)
- Администратор может создать один или несколько документов **Приход**, связанных с заявкой.
- В приходе указываются строки/количества ≤ «осталось оприходовать» по каждой позиции.
- После проведения прихода обновляется «оприходовано».
- Заявку можно перевести в «Получено», даже если часть позиций оприходована не полностью (с предупреждением в UI).
- Повторное открытие закрытой заявки в v1 не требуется.

Альтернатива UX (допустима при реализации): действие «Оприходовать выбранные» на странице заявки → создаёт и проводит StockIn.

### 6.7. История статусов заявки
`PurchaseRequisitionStatusHistory`: заявка, prev, new, дата, пользователь.

### 6.8. Права v1
Всё выполняет администратор.

## 7. Отчёты

Период «с — по», интерфейс в админке, экспорт XLSX (openpyxl).

### 7.1. Приход
Дата | Поставщик | Артикул | Наименование (рус) | Кол-во | Цена закупки ₽ | Сумма ₽  
Фильтры: период, поставщик.

### 7.2. Расход
Дата | № заказа | Клиент | Артикул | Наименование (рус) | Кол-во | Цена продажи ₽ | Сумма ₽  
Фильтр: период.

### 7.3. Остатки (на момент формирования)
Артикул | Наименование | On hand | Reserved | Available | Цена закупки ₽/ед. (средневзвешенная) | Стоимость по закупке | Цена продажи ₽ | Стоимость по продаже.

Средневзвешенная закупка — по проведённым приходам (партиям).

### 7.4. Движение за период
По каждому товару: остаток на начало + приход − расход = остаток на конец  
(резерв в этом отчёте не смешивать с расходом; при необходимости отдельная колонка «резерв на конец»).

## 8. Интерфейсы

### 8.1. Админ (Django Admin)
Кастомизация:
- inline для строк прихода, заказа, заявки, кроссов, применимости;
- actions / кнопки смены статуса заказа и заявки с проверкой инвариантов;
- удобный changelist заказов (новые сверху, цвет/фильтр);
- страницы отчётов + Excel;
- загрузка нескольких фото.

### 8.2. Клиент
Страницы: регистрация/вход; каталог; карточка; корзина; оформление; история; оферта/ПДн.  
Адаптивная вёрстка (desktop + mobile).

## 9. Структура данных (ключевые модели)

| Модель | Назначение |
|--------|------------|
| User | роль (admin/customer; manager — reserved), телефон |
| Category | дерево категорий |
| Product | номенклатура |
| ProductImage | фото |
| ProductCrossNumber | кроссы |
| CarMake / CarModel | справочник авто |

| StockMovement | журнал движений |

## 10. Нефункциональные требования

### 10.1. Стек
- Python 3.12+, Django 5.x
- SQLite в v1; настройки БД вынести в env — смена на PostgreSQL без переписывания логики
- Templates + Bootstrap 5
- openpyxl для отчётов
- Pillow для изображений

### 10.2. Безопасность
- HTTPS на хостинге
- CSRF, пароли Django validators
- Django Admin только для is_staff
- Media не исполняемые; ограничение типов файлов
- Защита от перебора логина (rate limit — желательно в v1, минимум через хостинг/fail2ban)

### 10.3. Надёжность
- Регулярный бэкап файла SQLite и папки media (описать в README: cron/панель Beget)
- Логи ошибок (хотя бы file logging)

### 10.4. Производительность
- До ~1500 товаров, один админ, умеренный трафик — SQLite допустим
- Индексы на normalized-полях поиска, FK, статусах заказов

### 10.5. Совместимость с будущим PostgreSQL
- Не использовать сырой SQL, завязанный на SQLite
- `select_for_update` в сервисном слое уже с расчётом на Postgres

## 11. Этапы сдачи и критерии приёмки

### Этап A — Каркас
Проект, User, категории, товары, фото, админка номенклатуры, кроссы, применимость.

**Приёмка:** CRUD товаров в админке; кроссы и авто сохраняются.

### Этап B — Витрина
Регистрация/вход, каталог, поиск (в т.ч. кроссы), фильтры, карточка.

**Приёмка:** поиск `ABC123` находит `ABC-123`; фильтр по марке/модели работает; вход по email+пароль без подтверждения почты.

### Этап C — Заказы
Корзина, оформление (самовывоз/доставка), резерв, статусы, история, список «Новые» в админке.

**Приёмка:** два параллельных сценария не уводят available в минус; отмена из «Новый» снимает резерв; подтверждение делает расход.

### Этап D — Склад и заявки
Поставщики, приход (проведение), заявка, частичный приход, статусы заявки.

**Приёмка:** два прихода по одной заявке корректно копят «оприходовано»; остатки сходятся с движениями.

### Этап E — Отчёты и деплой
Отчёты XLSX, выкладка на Beget, README (бэкапы, env), заглушки оферты/ПДн.

**Приёмка:** отчёты открываются и скачиваются; сайт открывается по домену.
